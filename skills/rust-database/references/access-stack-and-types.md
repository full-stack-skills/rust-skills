# Access Stacks and Types

## Selection Criteria

| Access Stack | Advantages | Requirements to Verify |
|---|---|---|
| SQLx | Direct SQL, asynchronous execution, connection pooling, optional compile-time checks | Database/Offline metadata, runtime/TLS features, dialect differences |
| Diesel | Typed DSL, schema generation, mature migrations | Synchronous/asynchronous adaptation methods, backend feature support, schema synchronization |
| SeaORM | Asynchronous ORM, entity and relationship models | Code drift from generated code, query shapes, migration compatibility with underlying dialects |
| Native Driver | Exposes database-specific features | Manual mapping, pooling, TLS configuration, error handling, maintenance overhead |

Prioritize continuing an existing and well-maintained access stack. If migrating the access stack first validate type safety, transaction behavior, performance characteristics, and operational costs using a representative read/write path before deciding to expand scope.

## SQLx Verification Checklist

- Confirm SQLx version, database driver, runtime environment, and TLS backend from `Cargo.lock` and feature tree;
- Ensure `query!`/`query_as!` macros have access to schema or offline metadata synchronized with the target schema;
- Note that at runtime mapping in `query_as` does not equate to compile-time SQL validation;
- When using dynamic SQL via QueryBuilder, always bind values and restrict identifier usage;
- Instantiate connection pools during process startup for reuse.

## Diesel Verification Checklist

- Keep migration scripts, actual schema definitions, and generated `schema.rs` files synchronized;
- Use the current version of the Diesel crate with its asynchronous adapter when connecting to transactions;
- Explicitly bind parameters in raw SQL statements and manually map results;
- Do not assume backend-specific DSLs are cross-database portable.

## SeaORM Verification Checklist

- Distinguish between entity models, active model representations, and transfer DTOs (Data Transfer Objects);
- Review the number of queries generated by `relation`/`preload`, avoiding N+1 query patterns;
- Ensure migrations can reproduce their output from version control history;
- Confirm that ORM features fully express required database-specific functionality. If not, use controlled raw SQL instead.

## Type Mapping Guidelines

- **Currency**: Use exact decimal or numeric types matching Rust idioms to avoid floating-point inaccuracies in monetary calculations;
- **Time**: Explicitly define UTC semantics versus local time zones and precision requirements;
- **IDs**: Confirm signed/unsigned variants, bit width, UUID encoding scheme, and external visibility constraints;
- **Nullable Fields**: Differentiate between "missing", `NULL`, default values, and patches where fields were not modified;
- **JSON Data**: Establish Rust types for stable JSON fields. For arbitrary JSON structures, implement schema/version strategies to ensure type safety;
- **Enums**: Define forward-compatible behavior for unknown enum variants during migration sequences.
